SDD v7 設計書

「最小限のファイルを育てる。非エンジニアが使えるシンプルさ。」

コア思想

原則: ファイルは最小限。新しく作るのではなく、既存ファイルにセクションを追記して育てる。
分割単位: ユースケース（UC）ではなく、機能単位。1機能に複数UCがぶら下がる。

規模による構成分岐

デフォルトは単一モード。ファイルが大きくなったら（目安: 300行超 or 5機能超）オーケストレーターがPOに分割を提案する。

単一モード（デフォルト）

specs/
  requirements.md   ← 全機能の要件
  design.md         ← 全機能の設計
  tasks.md          ← 全タスク（SoT）
機能が増えたら ## セクションを追記して育てる

分割モード（大規模時）

specs/
  overview.md       ← 全体像・機能間の関係
  {機能名}/
    requirements.md
    design.md
    tasks.md
overview.md で全体を俯瞰。機能フォルダは機能単位（UC単位ではない）

フェーズフロー

P1: 要件定義 pm 機能単位
specs/requirements.md に ## {機能名} セクションを追記
Mermaidユーザーフロー図を含む
↓ PO承認
P2: 設計 architect 機能単位
specs/design.md に ## {機能名} セクションを追記
specs/tasks.md にタスク行を追記
Mermaidアーキテクチャ図・シーケンス図を含む
↓ PO承認
P3: 実装 implementer 機能単位
src/ に実装、tests/ に受入基準のテスト（TDD）
バグがあった時だけ bugs/ に記録
▼ ここからプロジェクト全体 ▼
P4: レビュー + 仕様書き戻し reviewer 全体
プロジェクト全体を横断レビュー（セキュリティ含む）
実装で判明した事実を requirements.md / design.md に書き戻す
※ review.md は作らない。書き戻しが成果物。
↓ PO承認
P5: ドキュメント + コミット orchestrator 全体
CHANGELOG.md と README.md を更新
※ ADR・ガイド等は作らない。必要になったら作る。

フロー図（Mermaid）

flowchart TD
    PO[PO指示] --> P1

    subgraph feature["機能単位"]
        P1["P1: 要件定義\nrequirements.md に追記"]
        P2["P2: 設計\ndesign.md + tasks.md に追記"]
        P3["P3: 実装+テスト\nsrc/ + tests/"]
    end

    subgraph whole["プロジェクト全体"]
        P4["P4: レビュー + 仕様書き戻し\nrequirements.md / design.md 更新"]
        P5["P5: ドキュメント + コミット\nCHANGELOG / README 更新"]
    end

    P1 -->|PO承認| P2
    P2 -->|PO承認| P3
    P3 -->|全タスクDONE| P4
    P4 -->|PO承認| P5

    SCALE{ファイル300行超?\n5機能超?}
    SCALE -->|No| SINGLE[単一モード維持]
    SCALE -->|Yes| SPLIT["分割モードへ\noverview.md + 機能フォルダ"]

非エンジニア向け: 削除・簡略化リスト

「エンジニアのエンジニアによるエンジニアのための機能」を洗い出し。個人の非エンジニア開発では不要。
security エージェント
OWASP Top 10チェック専用エージェント。reviewer が最低限見れば十分。
削除
/log-review コマンド
外部AIに実行ログをレビューさせる。個人開発には不要。
削除
コンテキストリセット（P2→P3）
implementer に渡す情報を制限する仕組み。Claude Code の compaction に任せればよい。
削除
エージェントメモリ（.claude/memory/）
判断履歴の永続化。CLAUDE.md のメモ + specs ファイルで十分。
削除
Sub-agent制限表
誰が誰を呼べるかの制御表。個人開発ではオーケストレーター1人で十分。
削除
Hooks設定（settings.json）
PreToolUse / PostToolUse の自動チェック設定。エンジニアの設定作業が必要。
削除
/loop コマンド
定期実行。CI/CD的な使い方で個人開発には不要。
削除
Compaction管理ルール
コンテキスト70%超で提案。Claude Code が自動でやるので明示不要。
削除
パーミッション戦略（settings.json）
allow/deny リスト。エンジニアの設定作業が必要。
削除
コミットメッセージ形式
feat(Task-{N}): [要約] の強制。個人開発なら自由でよい。
簡略化
SPEC_GAP / SPEC_WRONG / SPEC_AMBIGUOUS
仕様ズレの報告マーカー3種。「仕様と違ったら書き戻す」のシンプルルールで十分。
簡略化
docs/adr/ （Architecture Decision Records）
設計判断の記録。design.md 内で「なぜこの設計か」を書けば十分。
削除
documenter エージェント
CHANGELOG/README更新だけならオーケストレーターが直接やれる。専用エージェント不要。
削除
バグなし記録（no-bugs.md）
バグがなくても空ファイルを作る。完全に不要。
削除

変更一覧

分割単位 UC（ユースケース）単位 → 機能単位（1機能に複数UCがぶら下がる）
レビュー review.md + security-review.md 新規作成 → 仕様に書き戻すだけ。専用ファイル廃止
承認フロー 4段階 (Large/Medium/Small/Trivial) → 2段階（要承認 / 自動進行）
テスト TDD + 単体・結合・受入テスト全部 → TDD維持。受入基準のテストのみ必須
バグ記録 バグなしでも no-bugs.md 必須 → バグがあった時だけ記録
セキュリティ 専用エージェント + 専用ファイル → reviewer が軽くチェック
受入基準 EARS記法5パターン → EARS記法を維持
仕様書き戻し SPEC_GAP/WRONG/AMBIGUOUS マーカー → P4で直接書き戻す。マーカー不要
steering docs product.md / tech.md / structure.md 3分割 → 3ファイル維持

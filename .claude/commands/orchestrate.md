# /orchestrate — 機能開発ワークフロー

POの指示から作業計画を立て、5フェーズで実行する。

## Step 1: 意図の解釈

POの指示を分析し、不明点があれば質問する：
- 誰が使うのか
- 何ができるようになるのか
- エラー時はどうなるのか
- スコープ外は何か

## Step 2: 承認レベル判定

| レベル | 判定基準 | PO承認ゲート |
|---|---|---|
| 要承認 | 新機能、設計変更、拡張 | Phase 1, 2, 4 |
| 自動進行 | ドキュメント修正、typo | 承認なし |

判定結果をPOに提示する。POは変更できる。

## Step 3: 5フェーズ実行

### Phase 1: 要件定義（pm）
- specs/requirements.md に `## {機能名}` セクションを追記
- Mermaid ユーザーフロー図を含める
- EARS記法で受入基準を記述
- → PO承認

### Phase 2: 設計＋タスク分解（architect）
- specs/design.md に `## {機能名}` セクションを追記
- Mermaid アーキテクチャ図・シーケンス図を含める
- specs/tasks.md にタスク行を追記
- → PO承認

### Phase 3: 実装＋テスト（implementer）
- TDDで実装（受入基準のテストのみ必須）
- バグがあった時だけ bugs/ に記録
- 1タスク = 1コミット
- 仕様と実態のズレがあればオーケストレーターに報告
- → 全タスク DONE で自動的に Phase 4 へ

### Phase 4: レビュー＋仕様書き戻し（reviewer）— プロジェクト全体
- プロジェクト全体を横断レビュー（セキュリティ含む）
- 実装で判明した事実を requirements.md / design.md に書き戻す
- review.md は作らない
- → PO承認

### Phase 5: ドキュメント＋コミット（orchestrator直接）— プロジェクト全体
- CHANGELOG.md を更新
- 必要に応じて README.md を更新
- 最終コミット

## 規模分岐チェック

Phase 2完了時に確認：
- specs/requirements.md or design.md が300行を超えていないか
- 機能が5つを超えていないか

超えている場合、分割モードへの移行をPOに提案する。
